# BUG-002 — Payment retry can create duplicate subscription charge

**Source ticket:** SUP-002  
**Severity:** Critical  
**Priority:** P0  
**Status:** Open  
**Escalation:** BILLING + ENG-BUG

## Environment

- Production-like web checkout
- Card payment flow
- Network throttling used to reproduce timeout/retry condition

## Preconditions

- Customer has no active Pro subscription.
- Valid payment method is available.

## Steps to reproduce

1. Start a Pro subscription purchase.
2. Submit payment while the network is artificially delayed.
3. Wait until the UI reports a timeout.
4. Click retry once.
5. Inspect resulting payment records.

## Expected result

The checkout should be idempotent. A retry for the same purchase attempt should create at most one successful charge.

## Actual result

Both payment attempts can complete successfully while the UI shows only one subscription purchase.

## Frequency

3/5 attempts under the tested timeout condition.

## Customer impact

Direct financial harm: a customer may be charged twice for one subscription purchase. Support also incurs refund and trust-recovery work.

## Immediate containment

- Escalate as P0.
- Flag affected transactions for billing review/refund.
- Avoid encouraging repeated retries while the defect is active.

## Investigation notes

The retry path appears to submit a second transaction without reusing an idempotency key from the original checkout attempt.

## Retest criteria

- Force the same timeout condition.
- Retry the checkout multiple times.
- Confirm exactly one successful payment and one subscription record.
- Confirm duplicate requests are safely rejected or mapped to the original transaction.
